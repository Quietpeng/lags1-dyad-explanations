lags1-dyad-explanations: actor-side components of dyadic event forecasts

Last updated 2026-11-01 · code release v0.1.2 at commit 70d6d78 · MIT (code only)

In short: lags1-dyad-explanations is the public artifact for a paper on actor-side components of dyadic event forecasts — a post-hoc six-class ownership convention applied to a plan-declared feature list, an exact additive decomposition of a logistic dyad-month forecast into source-role, target-role, dyad and non-actor parts, plus a matched-vintage audit — shipped as code, tests and frozen aggregate tables for a 196-actor ICEWS panel.

What ships is a contract plus an audit, not a framework. The decomposition is the logistic identity and coincides with linear SHAP under a training-mean background; it is not a new estimator.

What the ownership decomposition actually computes

A logistic regression on dyad-month features gives every prediction an exact additive decomposition, because the linear predictor is a sum of per-feature contributions. The repository fixes one owner per feature using a six-class convention applied after the fact to a plan-declared feature list, and also fixes the unit and the sign. Grouping the contributions by owner yields source-role, target-role, dyad and non-actor components that add up to the model's log-odds exactly — the notebook records a round-trip of 1.15e-14 on 50,000 evaluation rows (aggregate diagnostic only; the rows are not shipped).

Two numbers matter for reading the result honestly. On the V2 5.06 M-row training window the convention gives 45.2% actor-owned and 54.8% not actor-owned (README), which is the maximum of a 36.6-54.8% allocation range; if the dyad-specific neighbour-activity terms leave the actor class the figure is 63.2%. The V1 6.34 M-row fit gave 44.9/55.1 and 62.3, so the difference between vintages is at most 1.2 percentage points (results/). These shares describe the output of a convention, not a property of the actors, and the convention has no pre-run record — only the split carries an independently written pre-run timestamp.

Only 4 of the 49 features are role-specific: six of the seven source/target column pairs are one function of the same actor (five undirected graph terms plus the log in-plus-out ego count), so a "source" and a "target" effect often cannot be separated at all. That is a structural finding, not a bug in the code.

Frozen numbers you can verify locally

The plan-declared primary is a 49-feature logistic model on a one-shot, unit-fresh 20% dyad holdout: 311,638 dyad-months, 32,614 positives, 5,282 directed dyads, 2018-01-2022-11, not time-fresh. Its frozen metrics are log-loss 0.217875, AUC 0.910152 and AP 0.671863; against the train-only per-dyad Markov baseline it improves log-loss by 0.047999 (18.05%, holdout report), and against the stronger warm-history Markov baseline it improves AUC and AP but loses on log-loss by 0.008146 and on ECE by 0.031884. All of these come from README and the frozen tables under results/; the page adds nothing that is not there.

The V2 matched-vintage audit is a post-hoc secondary analysis of the same burned holdout. It removes three asymmetries one at a time: the two future-inclusive train-only columns, the 35-month vintage advantage of the warm comparator, and the H0 cache. After matching, the 47-feature model beats matched persistence by 0.020954, a 25-feature model with no actor-owned column beats it by 0.017743 (84.7% of the gain), and the 22 added columns contribute 0.003211 (15.3%). The honest claim boundary in the README is narrow: the supported statement is that the 47-feature contract beats matched persistence and the nested contrast excludes zero — not that actor-role content drives the gain.

Data availability and exclusions

This is an aggregate-only release, and the gap is deliberate. The following are withheld and must not be implied as downloadable anywhere: the licensed ICEWS v37 panel and any raw or derived event rows; row-level predictions and labels for the 311,638 evaluation rows; fitted coefficients, scaling arrays and feature/graph caches; the frozen V2 protocol directory; run logs; and the manuscript itself. The 50-refit audit code is restricted and not redistributed, and the public experiments/ scripts are a five-seed preview, not the restricted 50-refit audit.

What you do get is the verification layer: results/ with frozen aggregate tables, summaries and SHA256SUMS manifests; framework/ with the paper-path library; five executed read-only notebooks; and scripts/ with a release verifier, an aggregate checker and a preflight doctor. DATA_EXCLUSIONS.md lists every removed file and redacted column together with the machine checks that enforce the boundary, including the CSV rule that fails the release if any distributed table carries both a label and a prediction column.

FAQ

How do I decompose dyadic event forecast features by actor side?

Apply a fixed ownership convention to your feature list first — one owner per feature, plus a fixed unit and sign — then group the linear contributions by owner. This repository ships that convention as six classes and implements the grouping over a logistic dyad-month model in framework/; the same features also appear as a seven-class view in notebook 04, and the exact round-trip error is 1.15e-14 on 50,000 rows.

Is there a reproducible audit of feature attribution in a forecast model?

This repository is exactly that, within a deliberately narrow scope: frozen aggregates, SHA256SUMS manifests, contract and negative tests, and a release verifier that fails on forbidden columns. You can run make verify, make stability-check, make worldline-check and the notebook executor from the tree without any restricted input, and compare the numbers against the README.

Can I replicate an ICEWS panel event forecasting study with this code?

Partly. You can read and verify every frozen aggregate and re-render the notebooks, but you cannot regenerate the tables: that path needs the licensed ICEWS v37 panel, the restricted derived feature and graph caches, the local experiment configuration and row-level predictions, none of which are redistributed. Licensed access alone is not sufficient because the public tree has no cache-build entry point.

Does linear SHAP match the logistic decomposition?

Yes, under a training-mean background. The README states the decomposition is the logistic identity and coincides with linear SHAP under that background, which is why the artifact frames itself as a contract plus audit rather than a new estimator. The practical consequence is that the actor-side shares are a property of the convention and background you choose, not an identified causal quantity.

What data is not included, and can I download the ICEWS rows here?

No ICEWS rows ship here — not raw, not derived. Also withheld: row-level predictions and labels for the 311,638 evaluation rows, fitted coefficients, scaling arrays, feature and graph caches, the frozen protocol directory, run logs and the manuscript. Only aggregates, code, tests and notebooks are distributed, and DATA_EXCLUSIONS.md lists each removal with the check that enforces it.

What is the difference between the V1 result and the V2 audit?

V1 is the plan-declared primary of record: a 49-feature logistic model on a one-shot unit-fresh 20% dyad holdout, log-loss 0.217875. V2 is a post-hoc secondary analysis of the same burned holdout that removes the vintage and cache asymmetries; it cannot upgrade the V1 result and did not re-open the holdout. The 47-feature contract beating matched persistence by 0.020954 is the V2 statement, not a replacement for V1.

Does this repository have a DOI or an arXiv identifier?

No. There is no arXiv identifier, no paper DOI and no Zenodo DOI; the README says the arXiv link is still to be added, and the packaged metadata version stays 0.1.1 because no packaged byte changed between releases. Cite the code as v0.1.2 at commit 70d6d78 and the paper by its arXiv link once it exists. The only DOI on this page, 10.7910/DVN/28075, belongs to the ICEWS v37 dataset at the Harvard Dataverse, not to this paper.

Quick start

  1. python3 -m venv .venv && source .venv/bin/activate on Python 3.12 or newer.
  2. python3 -m pip install -r requirements.txt — the pinned numpy 2.5.4 and scipy 1.18.1 publish no 3.11 wheels.
  3. make doctor then make test for the public suite; make verify to check hashes, strict JSON, notebook outputs, forbidden paths and credential-like strings.
  4. Read the frozen results without Jupyter: load results/framework_pilot/holdout/summary.json and print status and primary.metrics.
  5. Optional: make notebooks re-renders the five shipped notebooks; it does not re-fit or re-score anything.
